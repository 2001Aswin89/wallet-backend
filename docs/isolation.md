# Isolation lab (Milestone 2, Step 1)

Generated by `python -m scripts.isolation_lab` on 2026-10-23 17:07 against 17.5. Two real connections, A and B, run the commands below against a scratch database built from this project's migrations (account 4 = main wallet, account 5 = savings wallet, both owned by user 1). Lines starting with `--` are comments added by the script; everything else is the actual command and result.

## Case 1 - Read Committed (the PostgreSQL default)

```text
A> BEGIN;
BEGIN
A> SELECT balance FROM accounts WHERE id = 4;
 balance
---------
    1000
(1 row)
-- session B changes the row and commits
B> BEGIN;
BEGIN
B> UPDATE accounts SET balance = 500 WHERE id = 4;
UPDATE 1
B> COMMIT;
COMMIT
A> SELECT balance FROM accounts WHERE id = 4;
 balance
---------
     500
(1 row)
A> COMMIT;
COMMIT
```

**Does A see a different value? Yes.** A read 1000, then 500 inside the same transaction. Each statement gets a fresh snapshot, so a committed change by B shows up (a non-repeatable read). This is why a plain read-then-write is unsafe: the value you checked may be stale by the time you write.

## Case 2 - Repeatable Read

```text
A> BEGIN ISOLATION LEVEL REPEATABLE READ;
BEGIN
A> SELECT balance FROM accounts WHERE id = 4;
 balance
---------
    1000
(1 row)
-- session B changes the row and commits
B> BEGIN;
BEGIN
B> UPDATE accounts SET balance = 500 WHERE id = 4;
UPDATE 1
B> COMMIT;
COMMIT
A> SELECT balance FROM accounts WHERE id = 4;
 balance
---------
    1000
(1 row)
-- A now tries to write based on what it saw (1000 - 10):
A> UPDATE accounts SET balance = balance - 10 WHERE id = 4;
ERROR:  could not serialize access due to concurrent update
-- SQLSTATE 40001
-- (session rolled back)
```

**What does A see now?** The same value both times (1000 then 1000): the snapshot is fixed at A's first query. But when A tried to *write* a row B had already changed, PostgreSQL refused with SQLSTATE `40001` ("could not serialize access due to concurrent update"). A must roll back and retry. Repeatable Read never lets you silently overwrite a change you could not see.

## Case 3 - Serializable (write skew)

```text
-- rule both sessions try to keep: the user's wallets together hold >= 1000
A> BEGIN ISOLATION LEVEL SERIALIZABLE;
BEGIN
B> BEGIN ISOLATION LEVEL SERIALIZABLE;
BEGIN
A> SELECT sum(balance) FROM accounts WHERE user_id = 1;
  sum
------
 2000
(1 row)
B> SELECT sum(balance) FROM accounts WHERE user_id = 1;
  sum
------
 2000
(1 row)
-- each sees 2000, so each thinks it may take 600 from a DIFFERENT wallet
A> UPDATE accounts SET balance = balance - 600 WHERE id = 4;
UPDATE 1
B> UPDATE accounts SET balance = balance - 600 WHERE id = 5;
UPDATE 1
A> COMMIT;
COMMIT
B> COMMIT;
ERROR:  could not serialize access due to read/write dependencies among transactions
DETAIL:  Reason code: Canceled on identification as a pivot, during commit attempt.
HINT:  The transaction might succeed if retried.
-- SQLSTATE 40001
-- (session rolled back)
A> SELECT id, balance FROM accounts WHERE id IN (4, 5) ORDER BY id;
 id | balance
----+---------
  4 |     400
  5 |    1000
(2 rows)
```

Both sessions read the same total (2000 and 2000) and each wrote a different row, which Repeatable Read would allow (write skew). **Under Serializable, 1 of the two transactions was aborted:** SQLSTATE `40001` "could not serialize access due to read/write dependencies among transactions". Final balances: [(4, 400), (5, 1000)]. Serializable keeps the result equal to *some* one-at-a-time order, at the price that the application must retry transactions that fail with `40001`.

## Case 4 - Repeatable Read with a join

```text
A> BEGIN ISOLATION LEVEL REPEATABLE READ;
BEGIN
A> SELECT a.id, a.balance, count(le.id) AS entries FROM accounts a JOIN ledger_entries le ON le.account_id = a.id WHERE a.id = 4 GROUP BY a.id, a.balance;
 id | balance | entries
----+---------+---------
  4 |    1000 |       1
(1 row)
A> SELECT count(*) AS phantom_check FROM ledger_entries WHERE account_id = 4;
 phantom_check
---------------
             1
(1 row)
-- session B adds a whole new ledger entry (a would-be phantom row) and updates the balance, then commits
B> BEGIN;
BEGIN
B> INSERT INTO transfers (type, status, amount, from_account_id, to_account_id, completed_at) VALUES ('top_up', 'completed', 500, 1, 4, now());
INSERT 0 1
B> INSERT INTO ledger_entries (transfer_id, account_id, direction, amount) SELECT max(id), 1, 'debit', 500 FROM transfers UNION ALL SELECT max(id), 4, 'credit', 500 FROM transfers;
INSERT 0 2
B> UPDATE accounts SET balance = balance + 500 WHERE id = 4;
UPDATE 1
B> COMMIT;
COMMIT
A> SELECT a.id, a.balance, count(le.id) AS entries FROM accounts a JOIN ledger_entries le ON le.account_id = a.id WHERE a.id = 4 GROUP BY a.id, a.balance;
 id | balance | entries
----+---------+---------
  4 |    1000 |       1
(1 row)
A> SELECT count(*) AS phantom_check FROM ledger_entries WHERE account_id = 4;
 phantom_check
---------------
             1
(1 row)
A> COMMIT;
COMMIT
A> SELECT a.id, a.balance, count(le.id) AS entries FROM accounts a JOIN ledger_entries le ON le.account_id = a.id WHERE a.id = 4 GROUP BY a.id, a.balance;
 id | balance | entries
----+---------+---------
  4 |    1500 |       2
(1 row)
```

**Does the guarantee still hold? Yes.** The join returned `(4, 1000, 1)` before B committed and `(4, 1000, 1)` after, in the same transaction. The snapshot covers every table the transaction reads, so the new ledger row did not appear either (count 1 then 1): no phantom. After A committed, a fresh read shows `(4, 1500, 2)`. (PostgreSQL's Repeatable Read is stronger than the SQL standard requires, which allows phantoms at this level.)

## Which level does the transfer use?

**Read Committed plus `SELECT ... FOR UPDATE`** on both account rows in ascending id order. The lock makes other transfers on those rows wait, and the balance is read *after* the lock is held, so the stale-read problem from Case 1 cannot hurt: the value checked is the value written against. Serializable would also be correct, but under contention on one hot wallet most transactions would abort with `40001` and need a retry (Case 3), which costs throughput for no extra safety here. Reconciliation is the exception: it runs at Repeatable Read because it needs one consistent snapshot across many tables (Case 4).
